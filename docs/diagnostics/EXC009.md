# EXC009: Exception contract does not match a required member

A source method, accessor, property, or event implements an interface member
that declares `[Throws]` or `[DoesNotThrow]`, but the implementation does not
declare an equivalent contract. Add the same attribution to the implementing
member, its property or event, or the containing class or struct. The code
fix adds that attribution when the implementation has no direct contract of
its own. It uses the string form of `[Throws]` and skips a generic exception
type.

The same warning applies to a source override of a method whose own contract
is `[DoesNotThrow]`, and to a source override or implementation of a no-throw
framework polyfill such as parameterless `ToString`, `Equals`, `GetHashCode`,
or `IComparable<T>.CompareTo`. Declare `[DoesNotThrow]` on the override, its
property or event, or a class or struct in its type hierarchy. A
`[DoesNotThrow]` on a parent class or struct is inherited and satisfies the
requirement. The base method's attribute alone does not: the override has to
state the contract. The code fix adds `[DoesNotThrow]` when the member has no
direct contract. It is not offered when the member already declares
`[Throws]`, because the two attributes conflict.

Equivalence is the same `[DoesNotThrow]` or the same set of exception types.
`[Throws("IOException")]` and `[Throws<IOException>]` match when they resolve
to the same type. A derived exception type is not the same published
contract as its base type. An inferred throw from the method body is not a
match.

This is the Exceptionable analog of nullable's interface-implementation
mismatch warnings, including CS8770 for a missing `[DoesNotReturn]`. Throw
and call diagnostics still use the intersection of the implementation and
every interface contract. A `[DoesNotThrow]` base method or no-throw polyfill
still reports EXC001 when a known exception escapes the override, including
when the override declares `[Throws]`. EXC009 does not replace EXC001, EXC002,
or EXC003.

An unannotated interface member does not require the implementation to omit
attributes. A base method `[Throws]` may still be replaced by the override.
When one method implements several interface members, each mismatched member
is reported. Explicit implementations can match each interface separately.
External implementations and methods inherited from a base class that does
not itself implement the interface are not reported. Compiler-generated
members, including a record's synthesized `ToString`, `Equals`, and
`GetHashCode`, are not EXC009. A different signature, such as
`ToString(string)`, does not inherit parameterless `ToString`.
